Building GymBuddy: A WhatsApp Bot That Detects Your Plateau Using Pure Python ML

How I built a gym tracker that knows when you're stuck — and tells you why.

By azzyth · Data Science student @ Telkom University · GitHub Repo

The Problem

Every lifter hits a plateau. You walk into the gym, do the same weight for the same reps, and nothing changes for weeks. The frustrating part isn't the stall — it's not knowing why. Are you under-eating? Cutting? Or is your program just done?

I built GymBuddy to answer that question. It's a WhatsApp bot (or terminal CLI) that logs your lifts and meals, then applies machine learning to detect plateaus and cross-reference your nutrition to explain the cause.

The ML: Pure Python, No Dependencies

The core is intentionally dependency-free. No numpy, no scikit-learn, no pandas. Just Python's standard library. This was a deliberate choice for three reasons:

  • Transparency — I can read every line of the math. No black-box sklearn calls.
  • Testability — tests run with unittest only. No pip install needed.
  • Portability — the core works on any Python install, including Raspberry Pi.

Step 1: Estimate 1RM (Epley Formula)

For each set, estimate the one-rep max using the classic Epley formula:

def epley_1rm(weight: float, reps: int) -> float:
    """Epley 1RM estimate."""
    if reps == 1:
        return weight
    return weight * (1 + reps / 30.0)

Step 2: Group by Day, Take Best

Raw sets are grouped by day (ts[:10]), and the best e1RM per day becomes a single data point. This prevents a high-volume day from being counted as "progress."

Step 3: Linear Regression on e1RM

Fit ordinary least squares on the (day_index, e1RM) points over a 6-week window. The slope tells you the trend in kg/week. 

def linear_trend(xs, ys):
    """Ordinary least squares. Returns (slope, intercept)."""
    n = len(xs)
    if n < 2:
        return 0.0, ys[0] if ys else 0.0
    mean_x = sum(xs) / n
    mean_y = sum(ys) / n
    num = sum((x - mean_x) * (y - mean_y) for x, y in zip(xs, ys))
    den = sum((x - mean_x) ** 2 for x in xs)
    if den == 0:
        return 0.0, mean_y
    slope = num / den
    intercept = mean_y - slope * mean_x
    return slope, intercept

Step 4: Flag the Plateau

A stall is flagged when either condition holds:

  • Recent 3-session trend ≤ 0%/week (you're going backwards right now)
  • Overall 6-week slope < 0.25%/week (barely moving even over a month)
Key insight: The 3-session check catches sudden stalls. The 6-week check catches slow drift. Using both prevents false positives from a single bad session.

The Nutrition Cross-Reference

This is where it gets interesting. When a stall is detected, the bot doesn't just say "you're stuck." It joins your food logs and body weight to name the cause:

  1. Under-fuelled — averaging below 90% of calorie target → fix food before program
  2. Cutting — body weight trending down → flatline is expected, hold the deload
  3. Programmed-out — eating at target, stable weight → training is the problem, deload 1 week then add volume
  4. No data — falls back to generic checklist

The priority order matters: if you're under-eating, that's the root cause regardless of what your program looks like. Fix the food first.

The Right-to-Left Parsing Trick

Exercise names have spaces: "bench press", "squat". Commands look like /set bench press 80 10 9 8. How do you parse the name from the numbers?

Parse right-to-left. Pop trailing tokens that parse as numbers. Everything remaining is the name. No quotes needed. 

# Right-to-left: pop numeric args from the end
parts = text.split()
args = []
while parts and _is_number(parts[-1]):
    args.insert(0, float(parts.pop()))
name = " ".join(parts).lower()  # "bench press"

Sparkline Downsampling

The /progress command shows a 20-character sparkline of strength over time. But what if you have 50 sessions? Average buckets, but keep the last bucket's true value so the tip always reflects current state. 

def _downsample(values, width=20):
    """Average buckets, but keep last bucket's true value."""
    if len(values) <= width:
        return values
    bucket_size = len(values) / width
    result = []
    for i in range(width):
        start = int(i * bucket_size)
        end = int((i + 1) * bucket_size)
        chunk = values[start:end]
        if i == width - 1:
            result.append(values[-1])  # tip = current
        else:
            result.append(sum(chunk) / len(chunk))
    return result

Double Progression: The /plan Command

Beyond detection, GymBuddy suggests your next session using double progression rules:

  • Hit top of range (12 reps) → add 2.5 kg, drop to 8 reps
  • In range (8-11 reps) → same weight, +1 rep
  • Below range (<8 reps) → back off 10%, rebuild

This is the hypertrophy standard (8-12 reps) applied algorithmically. No AI, no black box — just rules you could verify with a calculator.

Lessons Learned

  1. Pure Python ML is underrated. For simple regression on small datasets, you don't need scikit-learn. You need transparency and testability.
  2. Dependency injection for time. Passing now as a parameter instead of calling datetime.now() internally made every time-dependent test trivial.
  3. Right-to-left parsing. Parsing exercise names with spaces is annoying. Pop numbers from the right, everything else is the name.
  4. Single report builder, two consumers. Building the weekly report as a pure function (no WhatsApp session needed) made it testable in isolation.
  5. Evidence/auditability. Every plateau verdict shows the numbers it was drawn from. Users trust the bot more when they can see the math.
  6. Config-driven thresholds. All magic numbers live in config.py with env overrides. No hardcoded constants in business logic.
